# OCR 实测数据（2026-09-12，本机：RTX 4070 Ti SUPER / 20 核 CPU / 游戏已关闭）

测试素材：Deadlock 实机画面截图 1920×1080（`spike_out/region_raw.png`）。
引擎：RapidOCR 3.9.2，PP-OCRv6 det_small + rec_small，onnxruntime CPU。

| 场景 | 耗时 | 识别结果 |
|---|---|---|
| **校准好的小区域 420×60（det+rec）** | **101 / 103 / 105 ms** | 9 行，全部正确（`5`、`vs`、`7`、`2/1/0`、`45`、`06:49`…） |
| 单行紧裁剪（rec-only，无检测） | 54 ~ 131 ms/行 | **6/6 与 det+rec 完全一致** |
| 单行紧裁剪 加 40px 横向留白 | 91 ~ 127 ms | ❌ 开始出错（`45` → `E 45221`）→ **裁剪必须紧** |
| 底部 HUD 660×240（det+rec） | 92 ms | 0 行（该区域当时无文字） |
| 全屏 1920×1080（det+rec） | 1~4 秒 | 28 行；可用于"世界气泡猎取"，不能常驻跑 |
| 按行切条 rec-only（整屏 6~12 条） | 372 ~ 659 ms | ❌ 切条与真实行高对不上，会把多行粘成一串乱码 |

## 三条结论

1. **区域校准 + det+rec 是最优解**：把 OCR 区域框到聊天条那一小块，单帧约 100ms，
   3~5 fps 没问题，而且准确率最高。所以 `ocr.detect` 默认 `true`、区域默认尽量小。
2. **rec-only 只在"天生一行且裁剪紧"的场景用**（例如读聊天输入行）。
   留白一多就会串字，所以不要用它去啃整屏。
3. ⚠️ **OCR 引擎必须全局单实例**：两个 `RapidOCR()` 同时跑会互相抢 onnxruntime 线程，
   同一个 420×60 区域从 **101ms 恶化到 8603ms**（85 倍）。
   代码里已经用一把锁串行化，并且接收方向和"读输入行"共用同一个引擎。

## 复现方式

```powershell
python scripts/bench_ocr.py                    # 抓实时画面测
python scripts/bench_ocr.py --image spike_out/region_raw.png
```

> 注意：游戏运行时 OCR 会明显变慢（CPU 被游戏占用），上面数字是游戏关闭时的干净基线。
